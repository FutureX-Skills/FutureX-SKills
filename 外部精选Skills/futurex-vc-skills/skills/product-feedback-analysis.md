# Skill: product-feedback-analysis

## Purpose

用于从用户评价、社区讨论、客户访谈、销售通话和工单中提取 PMF 信号，判断产品是否解决真实痛点、用户是否愿意付费，以及当前产品缺陷会如何影响增长。

## When to use

- 公司声称已有用户喜欢、留存好或 PMF 明显时。
- 需要从评论、访谈或社区文本中寻找真实需求证据时。
- 产品型、开发者工具、AI 应用、SaaS 或消费类项目初筛和尽调时。
- 需要为客户访谈设计问题时。

## Inputs

- App Store、Product Hunt、G2、Reddit、Discord、GitHub issues、社群讨论等公开反馈。
- 客户访谈、销售通话、客服工单、NPS 或问卷。
- 产品说明、定价页、使用数据和客户画像。
- 竞品评论或替代方案反馈。

## Steps

1. 按来源、时间、用户类型整理反馈材料，标记来源类型和偏差风险。
2. 清洗反馈：去除重复内容、广告、无关情绪表达和无法判断语境的片段。
3. 聚类用户需求：痛点、使用场景、购买动机、替代方案、满意点、抱怨点、流失原因。
4. 提取 PMF 信号：高频主动推荐、强烈痛点、付费意愿、重复使用、切换成本、生产环境依赖。
5. 提取反向信号：低价值功能、体验问题、集成成本、可靠性差、价格异议、客户成功依赖过重。
6. 区分证据强度：真实客户原话、公开评论、公司整理的反馈、团队转述分别标记。
7. 将反馈映射到投资判断：目标客户是否清晰、需求是否刚性、市场是否可扩张、销售周期是否可控。
8. 输出后续客户访谈和产品验证问题。

## Quality checks

- 是否区分真实用户原话、公司转述和第三方评论。
- 是否说明样本偏差，例如早期粉丝、公开评论幸存者偏差、负面评论偏差。
- 是否把反馈转化为 PMF 和商业化判断。
- 是否列出需要客户访谈验证的问题。
- 是否避免从少量评论推出过强结论。

## Restrictions

- 不得编造数据。
- 不得把公司自述当事实。
- 不得泄露敏感材料。
- 不得编造用户反馈、客户名称、样本量、NPS、留存率或付费意愿。
- 不得泄露客户个人信息、联系方式、合同内容或访谈原文中的敏感信息。
- 不得把公司整理的用户反馈当作独立验证事实。
- 不得上传、外发或复制原始文件内容到外部服务。
- 必须遵守仓库根目录 `AGENTS.md`；如信息不足，必须明确标记「信息不足 / 待验证」并列出所需证据。
