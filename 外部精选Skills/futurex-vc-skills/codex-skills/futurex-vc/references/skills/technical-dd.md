# Skill: technical-dd

## Purpose

用于对技术型创业公司进行初步技术尽调，判断技术路线、产品架构、工程成熟度、可扩展性、安全性和技术壁垒是否支撑投资叙事。

## When to use

- AI、开发者工具、基础设施、硬科技或深技术项目进入复筛或尽调时。
- 公司声称拥有技术领先性、模型性能、专利壁垒或复杂系统能力时。
- 需要阅读代码库、架构文档、论文、白皮书或技术演示材料时。
- 投资 memo 需要技术风险和验证路径时。

## Inputs

- 技术白皮书、架构图、产品文档、API 文档、系统设计说明。
- GitHub repo、依赖清单、测试报告、性能 benchmark、部署说明。
- 专利、论文、模型卡、安全审计、客户技术反馈。
- 创始人或 CTO 访谈纪要。

## Steps

1. 明确技术 Claim：性能、成本、准确率、延迟、可扩展性、安全性、专利壁垒、差异化能力。
2. 标记每个技术 Claim 的来源类型和证据状态；公司演示和访谈默认写「公司自述」。
3. 如有代码库，阅读 README、目录结构、依赖、核心模块、测试、CI、配置和部署方式，形成代码上下文地图。
4. 如有架构文档，梳理数据流、关键服务、外部依赖、模型/算法组件、存储、权限和监控。
5. 检查工程成熟度：测试覆盖、错误处理、可观测性、文档、版本管理、安全实践、可维护性。
6. 检查技术壁垒：是否来自数据、算法、系统集成、客户 workflow、专利、团队经验或生态锁定。
7. 识别风险：技术指标不可复现、依赖第三方模型/API、数据合规、供应链安全、扩展成本、技术债。
8. 设计验证动作：复现实验、代码 walkthrough、客户技术访谈、日志/benchmark 底稿、红队测试、专家访谈。
9. 输出技术尽调结论和对投资判断的影响。

## Quality checks

- 是否把技术演示、benchmark、论文、代码证据分开标记。
- 是否明确哪些技术 Claim 尚不可复现。
- 是否区分技术新颖性、工程执行力和商业壁垒。
- 是否给出可执行的技术验证动作。
- 是否避免超出材料做专家式断言。

## Restrictions

- 不得编造数据。
- 不得把公司自述当事实。
- 不得泄露敏感材料。
- 不得编造性能指标、模型参数、代码质量、专利状态或安全审计结论。
- 不得泄露代码、密钥、客户数据、架构细节或安全漏洞。
- 不得把公司演示结果当作已验证事实。
- 不得上传、外发或复制原始文件内容到外部服务。
- 必须遵守仓库根目录 `AGENTS.md`；如信息不足，必须明确标记「信息不足 / 待验证」并列出所需证据。
